# Release Signing

Last updated: 2026-10-28

## Scope

Tariffia Wallet v1 targets two channels:

- Google Play: an Android App Bundle signed with a Play upload key, then re-signed by the Play app-signing key.
- Direct APK: an APK signed with a Tariffia-controlled release key.

F-Droid is deferred. F-Droid signs with its own key, so adding it later requires a separate assetlinks review.

## Key Model

Recommended model:

| Key | Purpose | Storage |
| --- | --- | --- |
| `tariffia-direct-release` | Signs direct-distribution APKs | Offline, encrypted, backed up |
| `tariffia-play-upload` | Signs AABs uploaded to Play | CI secret; resettable through Play Console |
| Play app-signing key | Signs Play-installed apps | Managed by Google |
| Debug/test key | Local debug builds only | Existing `app/test.keystore`; never production |

The direct release key cannot be reset by Google. If it is lost, existing direct-install users cannot receive updates signed by the same identity. The Play upload key can be reset through Play Console, but the Play app-signing key remains the identity of Play-installed apps.

A single key may be used for both direct APKs and Play uploads if operational simplicity is more important than isolating the two channels. That is not the recommended default.

## Before Generating Keys

1. Choose two custodians for the direct release key.
2. Prepare an encrypted offline backup location and a separate password manager entry.
3. Confirm the legal entity and certificate distinguished name to use.
4. Confirm the Play Console account and whether Play App Signing is already enrolled.
5. Use a trusted workstation with a current JDK. Do not generate or store production keys in the TariffiaCode PRoot guest, a shared CI workspace, or the repository.

Never send a keystore, private key, or password through chat, email, an issue, or a pull request.

## Key Parameters

Use these defaults unless a distribution requirement says otherwise:

- Keystore type: PKCS12
- Key algorithm: RSA
- Key size: 4096 bits
- Signature algorithm: SHA256withRSA
- Validity: 10000 days
- Alias: `tariffia-direct-release` or `tariffia-play-upload`
- Password: generated by a password manager, unique per key, at least 32 characters

Suggested distinguished name values must be confirmed by the project owner:

```text
CN=Tariffia Wallet
OU=Release
O=<legal entity>
L=<city>
ST=<region>
C=<two-letter country code>
```

## Generate the Direct Release Key

Run this interactively on the trusted workstation. Let `keytool` prompt for passwords so they do not enter shell history.

```bash
keytool -genkeypair \
  -v \
  -storetype PKCS12 \
  -keystore tariffia-direct-release.p12 \
  -alias tariffia-direct-release \
  -keyalg RSA \
  -keysize 4096 \
  -sigalg SHA256withRSA \
  -validity 10000
```

Record only the public certificate and fingerprint in project documentation. Keep the `.p12` file and passwords out of the repository.

## Generate the Play Upload Key

Generate a separate key if the project follows the recommended model:

```bash
keytool -genkeypair \
  -v \
  -storetype PKCS12 \
  -keystore tariffia-play-upload.p12 \
  -alias tariffia-play-upload \
  -keyalg RSA \
  -keysize 4096 \
  -sigalg SHA256withRSA \
  -validity 10000
```

Upload the public certificate to Play Console when enrolling in Play App Signing. Do not upload the direct release key.

## Fingerprints

Fingerprints are public identifiers, but they must come from the correct certificate.

For a keystore:

```bash
keytool -list -v \
  -keystore tariffia-direct-release.p12 \
  -alias tariffia-direct-release
```

Use the displayed `SHA256:` value, normalized to uppercase colon-separated hex.

For a built APK:

```bash
apksigner verify --print-certs app-release.apk
```

For a built AAB, use the upload certificate recorded in Play Console, not the Play app-signing certificate, unless you are checking the installed Play build.

The production assetlinks must contain:

- Play app-signing certificate fingerprint, for Play-installed apps.
- Direct release certificate fingerprint, for directly distributed APKs.
- Any additional certificate if another distribution channel is added later.

The development assetlinks must contain the debug certificate fingerprint used by debug/CI builds.

## Gradle Configuration Requirements

The implementation task must add a release signing configuration that:

- Reads the keystore path, keystore password, key alias, and key password from environment variables or an external properties file.
- Never falls back to `app/test.keystore` for a release build.
- Fails a release build when signing material is required but missing.
- Does not print secrets in Gradle output.
- Keeps `signingConfigs.test` for debug/CI builds only.

Suggested environment variables:

```text
TARIFFIA_KEYSTORE_FILE
TARIFFIA_KEYSTORE_PASSWORD
TARIFFIA_KEY_ALIAS
TARIFFIA_KEY_PASSWORD
TARIFFIA_REQUIRE_SIGNING
```

Suggested local-only file, if environment injection is inconvenient:

```text
~/.gradle/gradle.properties
```

Do not commit `keystore.properties`, `.p12`, `.jks`, `.keystore`, or passwords. The tracked `app/test.keystore` remains a public debug/test artifact and must never sign a release.

## CI Requirements

- Store the base64-encoded keystore only in protected CI secrets.
- Decode it into a temporary path with mode `600`.
- Pass passwords through environment variables or the CI secret store.
- Mask secrets in logs.
- Remove the temporary keystore in an `always()` cleanup step.
- Restrict release workflows to protected branches or manual approval.
- Do not expose signing secrets to pull requests from forks.
- Publish only artifacts produced by the protected workflow.

## Play App Signing

1. Enroll the app in Play App Signing.
2. Upload the Play upload certificate.
3. Download the Play app-signing certificate from Play Console.
4. Add its SHA-256 fingerprint to the production assetlinks.
5. Build and upload an AAB, not a directly signed APK, for Play distribution.
6. Verify the installed Play build with `apksigner verify --print-certs` where possible.

If Play App Signing is not used, the uploaded artifact's certificate becomes the installed app identity and must be protected accordingly.

## Direct APK Distribution

1. Build the release APK with the direct release key.
2. Verify the signature before publishing.
3. Compute SHA-256 and MD5 checksums.
4. Publish the checksums and release notes alongside the APK.
5. Keep the signing key offline; do not place it on the download server.

## Backup and Recovery

- Keep at least three encrypted copies of each keystore, on independent media or independent secure locations.
- Store passwords separately from the keystore files.
- Use two custodians for the direct release key.
- Test restoration into an isolated signing environment before the first production release.
- Document who can authorize a restore and how a compromised key is handled.
- Never test the only copy of a key by deleting or moving the original without a verified backup.

## Release Verification

Before publishing:

- [ ] The release build is signed by the expected certificate.
- [ ] The test certificate is not present on the release artifact.
- [ ] The certificate fingerprint matches the production assetlinks entry.
- [ ] The Play app-signing fingerprint matches the Play Console record.
- [ ] The direct APK fingerprint matches the direct distribution record.
- [ ] The checksum files were generated from the final artifact.
- [ ] No keystore or password appears in `git status`, CI logs, or build output.
